Enterprise intent to adopt hybrid retrieval tripled in a single quarter last year. At the same time, a new thesis emerged: per-session RAG is ending for agentic AI — replaced by knowledge pre-compiled for agent tasks.

Both can be true. Here is how I think about it after building [graph-rag-multi-hop](https://github.com/arnavhazra/graph-rag-multi-hop).

## Where per-session RAG breaks

Agents chain ten queries, not one. Each hop re-retrieves, re-embeds, re-ranks. Latency compounds. Context windows fill with redundant chunks. Multi-hop questions break naive similarity entirely.

## The compilation-stage alternative

Pre-compile domain knowledge into structures agents traverse:

- Entity-relationship graphs (Neo4j) for multi-hop reasoning
- Dense indexes (Qdrant) for semantic fallback
- Rerankers on the union of both signals

The agent navigates a knowledge layer; retrieval becomes lookup, not search.

## Hybrid is the bridge I shipped

1. Ingest → extract entities → graph + vector stores
2. Query → resolve entities → Cypher paths + vector search
3. Union → rerank → LLM window

Benchmark on my engine: **2-hop graph traversal in 3.4ms**. Triple extraction at ~42ms/KB. Docker Compose away from reproducible evaluation.

## When to compile vs. retrieve

| Pattern | Best for |
|---|---|
| Per-session RAG | Small, dynamic corpora |
| Compilation-stage | Stable domain knowledge |
| Hybrid graph + vector | Multi-hop + semantic precision |

If you are building agents on enterprise knowledge, the question is not "which vector DB?" — it is "what structures do my agent tasks actually need?"
